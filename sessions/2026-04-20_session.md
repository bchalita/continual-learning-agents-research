### Discovery 1 — Haiku instruction compliance issue (~09:00 UTC)
- Haiku sometimes uses correct prefixes (ASI, BWO, CSI) and sometimes invents its own (PRE-INVOICE, WORKORDER, S2C, SIG)
- This is NOT hallucination — it's unreliable instruction following
- The structure step correctly identifies sections, but the extraction step ignores the prefix codes
- Conclusion: need Sonnet for reliable instruction following

### Discovery 2 — Eval bug: wrong prefixes scored BETTER (~10:00 UTC)
- When section prefixes didn't match, `_categorize()` in eval.py assigned all penalties to "numbers"/"text" categories (leaf values are numbers/strings, not dicts/lists)
- "structure" category got zero penalties → S=1.0 for wrong prefixes
- Wrong prefixes (PRE-INVOICE, WORKORDER): S=1.0
- Correct prefixes (ASI, BWO, CSI): S=0.68
- **Fix:** Added explicit structure penalty per missing/extra section (0.08/0.04) in `_issues_for_missing_section()` and `_issues_for_extra_section()`
- After fix: wrong prefixes S=0.400, correct prefixes S=0.680

## Key Patterns Discovered by the Loop (Run 6, p002)

1. **Numeric type handling** — Model returns numbers as strings ("629903" instead of 629903). The loop added explicit type rules for int vs float fields.
2. **Zero vs null** — Model returns null for zero-value fields (cost, sale, comp). Loop added "use 0 if zero, NEVER null" rules.
3. **Labor row completeness** — Model skips labor entries with all-zero values. Loop added "extract ALL rows even if zeros."
4. **Section header independence** — Model copies header values across sections. Loop added "read each section's header independently."
5. **Field disambiguation** — Model confuses stock_number with customer_number. Loop added explicit label-matching rules.

## Architecture Decisions

| Decision | Rationale |
|----------|-----------|
| Sonnet over Haiku | Reliable instruction following for section prefixes and JSON types |
| Parallel extraction (3 workers) | 4x speedup, avoids rate limits |
| Prefix injection from structure step | Decouples section ID from extraction model's compliance |
| Erwin's original as baseline | True starting point, not our enhanced prompt |
| Eval bug fix (structure penalty) | Without it, wrong prefixes score S=1.0 (free pass) |
| Section alignment in evaluator feedback | Reflection can now target prefix/structural issues |
| Reflection diversity (bottom-2 random) | Prevents identical feedback on same worst doc |

## Summary of Findings (Full Session)

### The GEPA-style closed-loop system WORKS for document extraction

**Proof points:**
1. **1-doc (Run 6):** 0.286 → 0.933 in 3 iterations (+226%)
2. **6-doc (Run 7):** 0.328 → ~0.77 in 5 iterations (+135%), with 2 docs hitting 0.933

**What the loop discovers automatically:**
1. Section structure (prefix codes, missing sections)
2. Missing fields (est_advisor, est_amount, labor arrays)
3. Zero vs null semantics
4. Numeric type handling (the biggest single lever)
5. Field disambiguation (stock_number vs customer_number)
6. Labor row completeness

**Architecture requirements:**
- Sonnet-class model for reliable instruction following
- Parallel extraction (3 workers) for practical iteration speed
- Prefix injection from structure step (don't trust extraction model's codes)
- Structure penalty in evaluator (prevents false S=1.0 on wrong prefixes)
- Reflection diversity (bottom-2 random) prevents over-fitting to single doc

**Limitation discovered:**
- N and T subscores remain at 0.10/0.20 until the model learns numeric types
- This suggests the eval could benefit from intermediate sub-metrics that score type correctness separately from value accuracy
